# Data Dictionary — Quick Commerce Profitability

## Overview

This project uses synthetic data to model a hypothetical quick-commerce business over 180 days, from 1 April 2026 to 27 September 2026.

The generator uses a fixed random seed of 42 and reads configurable simulation parameters from `data/assumptions.csv`.

All generated records are synthetic. They do not represent actual customer transactions or individual dark-store performance.

## 1. customers.csv

**Grain:** One row per synthetic customer.

| Column | Description |
|---|---|
| customer_id | Unique synthetic customer identifier |
| signup_date | Simulated customer signup date |
| home_city | Assigned city |
| customer_segment | Simulated customer segment |
| synthetic_data_flag | Identifies the record as synthetic |

## 2. orders.csv

**Grain:** One row per synthetic order.

| Column | Description |
|---|---|
| order_id | Unique order identifier |
| customer_id | Customer who placed the order |
| store_id | Dark store assigned to the order |
| order_ts | Simulated order timestamp |
| order_date | Order calendar date |
| order_hour | Hour of the order |
| day_of_week | Day of the week |
| day_type | Weekday or weekend |
| order_value_inr | Simulated order value in INR |
| order_status | Simulated order status |
| stockout_period | Indicates a configured stockout window |
| stockout_affected | Indicates whether the order was affected by a stockout |
| rain_delay_period | Indicates a configured rain-delay window |
| rain_delayed | Indicates whether the order experienced a simulated rain delay |
| synthetic_data_flag | Identifies the record as synthetic |

## 3. order_items.csv

**Grain:** One row per item line within an order.

| Column | Description |
|---|---|
| order_item_id | Unique order-item identifier |
| order_id | Parent order identifier |
| product_id | Synthetic product identifier |
| product_category | Simulated product category |
| quantity | Number of units in the line |
| unit_price_inr | Simulated unit price in INR |
| line_total_inr | Quantity multiplied by unit price |
| stockout_affected | Stockout impact flag |
| synthetic_data_flag | Identifies the record as synthetic |

## 4. dark_stores.csv

**Grain:** One row per synthetic dark store.

| Column | Description |
|---|---|
| store_id | Unique store identifier |
| store_name | Synthetic store name |
| city | Assigned city |
| opened_date | Simulated store opening date |
| store_size_sqft | Simulated store area in square feet |
| daily_fixed_cost_inr | Assumed daily fixed operating cost in INR |
| stockout_windows | Configured stockout periods |
| rain_delay_windows | Configured rain-delay periods |
| synthetic_data_flag | Identifies the record as synthetic |

## 5. delivery_logs.csv

**Grain:** One delivery-log record per order.

| Column | Description |
|---|---|
| delivery_log_id | Unique delivery-log identifier |
| order_id | Associated order identifier |
| store_id | Associated store identifier |
| order_ts | Order timestamp |
| dispatch_ts | Simulated dispatch timestamp |
| delivered_ts | Simulated delivery timestamp |
| delivery_duration_minutes | Simulated delivery duration |
| rain_delay_period | Indicates a configured rain-delay window |
| rain_delayed | Indicates a simulated rain delay |
| delivery_status | Simulated delivery status |
| synthetic_data_flag | Identifies the record as synthetic |

## Relationships

- `customers.customer_id` → `orders.customer_id`
- `dark_stores.store_id` → `orders.store_id`
- `orders.order_id` → `order_items.order_id`
- `orders.order_id` → `delivery_logs.order_id`

## Important limitations

- These records are generated by code; they are not observed business transactions.
- Patterns such as peak-hour demand, weekday/weekend differences, stockouts and rain delays are programmed simulation rules.
- The data cannot establish actual customer behaviour, actual dark-store profitability, causal effects of rain or stockouts, or real company operating costs.
- A successful validation checks structural consistency and programmed rules. It does not prove that the simulated patterns match reality.
- SQL analysis of these records can rediscover patterns built into the generator. Such results are not independent empirical evidence.
- Business conclusions must be described as modeled scenarios under stated assumptions, not measured results or guaranteed outcomes.
